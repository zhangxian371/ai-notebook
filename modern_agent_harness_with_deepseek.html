Agent / Harness 学习笔记

现代 Agent Harness 的基本工作模型

——先理解通用 Agent 怎么工作，再看 DeepSeek Harness 是怎么把它实现出来的。

先把两层分开

学习 Harness 时最容易混淆的是两件事：

第一层：通用 Agent / Harness 概念 回答： “一个现代 Agent 一般是怎么工作的？” 第二层：DeepSeek Harness 的具体实现 回答： “DeepSeek 用什么软件架构把这些能力组织起来？”

LLM、Agent Loop、Tool、Sandbox、Session 可以作为理解现代 Agent 的通用概念。

Cordis、ctx、Service、inject 则属于 DeepSeek Harness / Cordis 的具体实现方式。

第一章：先不管 DeepSeek，现代 Agent 是怎么干活的？ 这一章建立通用心智模型，不讨论 DeepSeek 的具体源码设计。

1. Harness 是什么？

Harness

普通英语里有“挽具、束具、把力量组织起来使用”的意思。在 Agent 领域，可以先理解成：把 LLM、工具、上下文、执行环境等组织起来，让模型能够持续完成任务的运行系统。

单独一个 LLM，往往更像：

用户 ↓ LLM ↓ 回答

有了 Harness 后，变成：

用户任务 ↓ LLM 思考 ↓ 调用工具 ↓ 看到结果 ↓ 继续思考 ↓ 继续执行 ↓ 直到任务完成
可以先把 Harness 理解成：让 LLM 从“会回答”变成“能持续干活”的那一整套外围系统。

2. 五个核心角色

LLM
大脑 / 技术专家

负责判断下一步应该做什么。

Agent Loop
项目经理 / 流程控制器

负责不断推进“想 → 做 → 看结果 → 再想”。

Tools
手脚 / 工具箱

负责读文件、改文件、执行 shell、搜索等真正的动作。

Sandbox
工作间 / 权限边界

规定工具在哪里执行，以及允许碰哪些资源。

Session
工作档案 / 过程记录

保存这一趟任务中前面发生过什么。

3. 一次真实任务怎么跑？

假设你说：

帮我把这个 C++ 项目的编译错误修掉。

第一步：Agent Loop 去问 LLM

Agent Loop ↓ LLM

LLM 判断：

先执行 make，看看实际编译错误。

这里 LLM 只是做出判断，它本身通常不会真的执行 make。

第二步：Agent Loop 调用 Tool

LLM： “执行 make” ↓ Agent Loop ↓ Tool

第三步：在 Sandbox 中执行

Tool ↓ Sandbox ↓ /workspace/project ↓ make
main.cpp:52: error: ...

第四步：把结果交回去

Sandbox ↓ Tool ↓ Agent Loop ↓ Session 记录 ↓ LLM 再分析

LLM 看完报错后继续判断、修改、重新编译，直到任务完成。

4. 最容易混淆：LLM 和 Agent Loop

Loop

英文就是“循环”。所以 Agent Loop 可以先理解成“Agent 的循环执行过程”。

LLM = 想。

Agent Loop = 让“想、做、观察、再想”循环起来。

while (!finished) {
    Action action = llm.think(context);

    if (action.isToolCall()) {
        Result result = tools.execute(action);
        context.add(result);
    } else {
        finished = true;
    }
}

真实系统会复杂得多，但这段伪代码足以建立第一层直觉。

5. Tool 和 Sandbox 的区别

Sandbox

字面是“沙箱”。现实里的沙箱是一个有边界的玩耍区域；软件里的 Sandbox 也强调：可以运行，但活动范围被限制在一个边界内。

概念回答的问题现实类比
Tool能干什么？锤子、电钻、扳手
Sandbox在哪里干？能干到什么程度？工厂车间、受控工作区

因此，“Agent 有 bash 工具”不等于“它可以在你的电脑上随便执行任何命令”。

6. Session 是什么？

Session

普通英语里有“会话、一次连续活动”的意思。在这里可以先理解成：这一趟任务的工作档案。

用户：修 bug LLM：先 make Tool：make Result：第 52 行报错 LLM：修改第 52 行 Tool：edit Tool：make Result：成功

这些过程需要被记录下来，否则下一轮 LLM 就不知道前面发生过什么。

第一章只记这五问

问题对应组件
谁负责想？LLM
谁负责让流程不断推进？Agent Loop
谁负责真正动手？Tools
在哪里动手、权限边界是什么？Sandbox
前面发生过什么？Session

现代 Agent Harness 可以先感性地理解成：一个不断重复“想一下 → 动一下 → 记录一下”的机器。

8. Cordis 是什么？

Cordis

这是一个专有名称，不是软件工程里“框架”的通用单词。在 DeepSeek Harness 中，可以先把它理解成：负责组织插件、服务和生命周期的底层插件框架。

如果把 DeepSeek Harness 看成一座办公楼，Cordis 更像：

门禁、电梯、房间编号、供电接口和物业系统。

它本身不负责“修 C++ bug”，但负责让真正做事的模块能够被加载、找到彼此、声明依赖并正常协作。

9. Context / ctx、Service、Plugin

Context / ctx

Context 是“上下文、运行环境”；ctx 是常见缩写。在 Cordis 里，可以粗略理解成：一个集中拿各种服务的运行时上下文。

Service

普通英语是“服务”。软件里常表示：一个模块对其他模块提供的稳定能力/API。

Plugin

来自 plug in，字面就是“插进去”。这里更适合理解成：可插拔模块。

某个 LLM Plugin │ │ 提供 ▼ llm Service │ ▼ ctx.llm ▲ │ 使用 │ Agent Loop Plugin

于是 Agent Loop 不需要知道下面究竟是 DeepSeek、Claude 还是其他模型，只需要知道：“这里有一个 llm 服务可以用。”

10. “一切皆插件”到底是什么意思？

它并不是说整个系统真的所有东西都是插件。

更准确的理解：凡是可能变化、可能替换、可能存在多个实现的能力，都尽量做成可插拔模块。

例如今天：

LLM = DeepSeek Sandbox = 本地环境 Session = 某种本地存储 Agent Loop = 一步一想、一做

以后可以换成：

LLM = 另一个模型 Sandbox = Docker / 远程环境 Session = 另一种存储 Agent Loop = Planner + Executor

如果接口保持一致，Harness 的核心组织机制不需要跟着大改。

11. 最后把两层重新叠起来

══════════ 通用 Agent / Harness 心智模型 ══════════ Agent Loop │ ┌────────┼────────┐ ▼ ▼ ▼ LLM Tools Session │ Sandbox 想 → 做 → 看结果 → 再想 ════════ DeepSeek Harness 的具体架构 ═════════════ Cordis │ Context / ctx │ Service / Plugin │ ┌────────────┼────────────┐ ▼ ▼ ▼ LLM能力 Tool能力 Loop能力 │ │ │ 可替换 可替换 可替换

所以不要把 Cordis、ctx、inject 当成所有 Agent 都必须使用的通用术语。它们只是 DeepSeek Harness 给通用 Agent 问题提供的一套具体软件架构答案。

整篇最终结论

第一层：先学会看懂 Agent 的工作过程——LLM 想、Agent Loop 推进、Tool 动手、Sandbox 限制执行环境、Session 保存过程。

第二层：再看 DeepSeek Harness 如何用 Cordis、Plugin、Service、ctx 等机制，把这些能力做成一套可组合、可替换的软件系统。

通用原理先于具体实现。这样以后再看 Codex、Claude Code、OpenClaw、Hermes，也能使用同一套心智模型，而不会把某一个项目的实现方式误认为 Agent 的唯一标准。
