Sandbox / 沙盒

程序员在谈 Sandbox 时，到底在谈什么？

先不谈 Harness，也先不钻 namespace、cgroups、seccomp 的实现细节。 只看一个最重要的问题：如何让一段“不完全可信”的程序可以运行，但又不能把整台机器搞坏。

可以把 Sandbox 先理解成：给程序一个“受控的小世界”运行。
它可以做事，但能看到什么、能用多少资源、能做哪些动作、什么时候结束，都由外面控制。
1

隔离 Isolation

这个程序能“看到”什么？

沙盒要把程序和宿主机隔开。程序通常不应该随便看到宿主机上的进程、文件、网络环境等。

典型问题：
能不能看到 /home？
能不能看到其他用户的进程？
能不能访问宿主机真实网络？
2

资源限制 Resource Limits

它最多能消耗多少东西？

即使程序没有恶意，只是写了死循环、内存泄漏、无限创建线程，也不能让它拖垮整台服务器。

常见限制：
CPU 时间、内存、进程数、线程数、磁盘空间、运行总时长。
3

权限 Permission

它“允许做”什么？

能看见某样东西，不代表一定允许操作它。沙盒通常还会进一步限制文件、网络、系统调用等权限。

典型问题：
能不能写文件？
能不能访问公网？
能不能执行任意系统调用？
能不能启动新的程序？
4

生命周期 Lifecycle

这个“小世界”什么时候出生、什么时候销毁？

Sandbox 往往不是永久存在的。一个任务来了，创建环境；程序运行；任务结束后清理。

典型流程：
创建 → 放入代码/数据 → 启动 → 监控 → 超时/结束 → 销毁。
5

性能与成本 Performance / Cost

隔离得越狠越好吗？不一定。

如果每运行一个小程序都启动一整台虚拟机，安全性可能很好，但启动慢、占内存、成本高。 所以实际工程里一直在权衡：隔离强度、启动速度、资源占用、兼容性。

核心权衡： “这个场景到底需要多强的隔离，才能既安全，又不至于太重？”

一个最直观的场景：在线运行 C++ 代码

假设我们做一个简化版 LeetCode：用户上传 main.cpp，服务器替他编译并运行。

上传代码 → 编译 → 沙盒中运行 → 返回输出 → 销毁环境

如果用户写了 while(true) {}， 沙盒不需要理解“这是不是死循环”，只需要保证： 超过 2 秒还没结束，就终止这个任务。

如果程序疯狂申请内存，也不需要先分析代码，只需要规定： 最多给你 256 MB，超过就杀掉。

这就是 Sandbox 一个非常重要的思维： 不一定提前证明程序绝对安全，而是把它可能造成的后果控制在一个边界里。

一句话记忆：
Sandbox 讨论的核心不是某一个 Linux 技术，而是： 隔离什么、限制什么、允许什么、活多久，以及这么做要付出多少成本。
后面再学习 namespace、cgroups、seccomp、容器、虚拟机时， 可以把它们看成是在回答上面这些问题的不同“实现零件”。
