前端学习笔记：从 Resource 思想到 REST、可寻址性与缓存

—— 接上一篇《HTML 与 HTTP 理解》3.4 节"Resource 思想"

1. 重提 Resource 思想

上一篇说：HTTP 不关心内容类型，只关心资源。资源可以是图片、用户、文章、视频——任何能通过 URL 寻址的东西。

这个抽象看似平淡，其实蕴含 Web 架构的三个支柱：

  • 可寻址性 (Addressability)：每个资源都有稳定地址
  • 统一接口 (Uniform Interface)：用同一套方法操作所有资源
  • 可缓存性 (Cacheability)：资源可以安全地缓存在中间层

这三条加起来，就是 REST。

2. REST 是什么、不是什么

2.1 定义

REST（Representational State Transfer）是 Roy Fielding 在 2000 年博士论文里提出的一种架构风格（Architectural Style），不是协议、不是标准、不是框架。

它规定了 6 个约束：

  • Client-Server：关注点分离
  • Stateless：无状态（上一篇 3.7 节提过）
  • Cacheable：可缓存
  • Uniform Interface：统一接口
  • Layered System：分层系统
  • Code on Demand（可选）：代码按需下发，比如 JavaScript

2.2 关键在"统一接口"

6 个约束里最容易被忽视也最重要的是第 4 条，它又有 4 个子约束：

  • 资源识别 (Identification of resources)：通过 URI
  • 通过表征操作资源：客户端拿到的是资源的"表征"（HTML、JSON、XML），不是资源本身
  • 自描述消息 (Self-descriptive messages)：消息要带足够信息让对方理解
  • 超媒体作为应用状态引擎 (HATEOAS)：响应里要带链接，告诉客户端下一步能去哪

2.3 常见的误解

「REST 就是用 GET / POST / PUT / DELETE 四个动词」

错。这只是"统一接口"的表层。真正的 REST 要求你重新设计资源的边界：

❌  /api?action=deleteUser&id=123
✅  DELETE /users/123

❌  /api?type=getArticle&id=456
✅  GET /articles/456

❌  /api/updateProfile
✅  PATCH /users/me

动词藏在 URL 里 = RPC 风格，URL 是"函数调用"。
动词在 HTTP method 里 = REST 风格，URL 是"资源地址"。

3. 可寻址性：URL 是资源的"身份证"

3.1 什么是可寻址性

Web 上的每一个资源（HTML 页面、图片、文章、用户、视频）都应该有一个稳定、唯一、可被引用的 URL。

这就是 Web 和桌面应用最本质的区别：

  • 桌面应用里，文档通过"文件路径 + 操作系统"寻址
  • Web 里，文档通过"URL + HTTP"寻址

URL 是 Web 世界的对象引用。

3.2 为什么这一点是革命性的

在 Web 出现之前，"信息孤岛"是常态：

  • Word 文档只能在装了 Word 的机器上打开
  • 数据库里的记录只能通过特定程序访问
  • 一篇论文要引用另一篇论文，只能在文末写"见参考文献 [3]"

Web 的解法：把所有信息都"挂"在一个全局可寻址的地址空间上。一旦一个东西有了 URL，它就可以：

  • 被链接
  • 被收藏
  • 被搜索引擎收录
  • 被缓存
  • 被版本化
URL = 地址 + 标识符 + 分类标签，三位一体。

3.3 好的 URL 设计原则

✅ 语义化
   /articles/2026/06/rest-and-addressability
   而不是 /index.php?id=12345&action=view

✅ 稳定
   /users/371  而不是 /users/371?v=2

✅ 可猜测
   /users/371/articles
   /users/371/comments
   /articles/123/author
   而不是 /getAuthorByArticle?article=123

一个稳定的 URL 是一个长期承诺。一旦你改了它，外部所有引用都会失效——书签、搜索引擎、其他网站的链接，全断。

这就是为什么"URL 设计"在严肃的 Web 系统里被视为架构决策，而不是命名问题。

4. 缓存：HTTP 为什么从一开始就支持缓存

4.1 缓存的三个前提

HTTP 能缓存，依赖三个前提缺一不可：

  1. 可寻址性：同一个 URL 必须指向同一个资源（否则缓存无意义）
  2. GET 是安全的 (Safe)：GET 不修改服务器状态
  3. GET 是幂等的 (Idempotent)：多次执行 GET 不会产生副作用

这三条加起来，中间节点（浏览器、CDN、反向代理）才能放心地替你重复请求同一个 URL。

4.2 缓存的两层机制

时间维度：

  • 资源有"过期时间"（Cache-Control: max-age=3600）
  • 过期前直接用本地副本
  • 过期后用"条件请求"问一下服务器（If-None-Match、If-Modified-Since）

内容维度：

  • 资源有"指纹"（ETag、Last-Modified）
  • 指纹一致 → 服务器返回 304 Not Modified，零字节
  • 指纹不一致 → 服务器返回 200 + 新内容

4.3 缓存不只是性能优化

很多人把缓存当成"加速器"，但更准确的理解是：

缓存是"无状态"这个设计的代价补偿器。

上一篇说 HTTP 是无状态的——服务器不知道也不记得你请求过什么。这意味着每次请求都要重新计算或重新传输。在物理上，这是巨大的浪费。

缓存机制让"无状态"在保持简单的同时，获得了接近"有状态"的效率：

  • 浏览器缓存：让 Web 应用的"冷启动"几乎为零
  • CDN 缓存：让全球用户都能从最近的节点拿到资源
  • 反向代理缓存：让一台 Nginx 顶住 10 倍流量

这就是为什么 CDN 这件事能成立——它不是另一个网络，而是一层被 HTTP 协议设计"邀请"进来的中间层。

5. 三者怎么咬合在一起

把上面三节串起来，是一条因果链：

可寻址性 (URL 稳定)
      │
      ▼
GET 才有意义 (安全 + 幂等)
      │
      ▼
缓存才安全 (中间节点可以重发)
      │
      ▼
系统才能扩展 (CDN、代理、浏览器)
      │
      ▼
Web 才能跑到全球规模

每一环都是上一环的必然结果。

这就是 REST 真正的力量——不是"用对 HTTP 动词"，而是这套约束组合在一起，让系统获得了可寻址性、可缓存性、可扩展性、简单性。

Fielding 当年设计这些约束，不是为了让 API 长得"规范"，是为了让 Web 这个全球规模的信息系统能跑起来。

6. 实战含义

6.1 为什么"改 URL"是事故

旧: /api/v1/users/371
新: /api/users/371

这种"小改"实际意味着：

  • 客户端代码全要改
  • 第三方集成都失效
  • 搜索引擎收录全断
  • 用户收藏的书签全错

→ URL 是公开契约，不是内部实现。

6.2 为什么"内容存数据库 + API 动态生成"不是唯一选择

上一篇 4 节提到"静态站用 GitHub Pages 就能发"。从这一篇的角度看：

  • 静态文件天然可寻址（文件名就是 URL）
  • 静态文件天然可缓存（Nginx 直接 sendfile）
  • 静态文件天然可分发（推到 CDN 即可）

→ 静态不是"过时的技术"，是 REST 架构的最纯粹实现。

6.3 为什么 GraphQL 不是 REST 的"升级"

GraphQL 解决了"客户端需要灵活查询"的问题，但代价是：

  • 失去了 URL 级别的可寻址性（一个 query 一个 endpoint）
  • 失去了 HTTP 缓存（POST /graphql 没法用 URL 缓存）
  • 引入了额外的中间层（Schema、Resolver）

→ GraphQL 是在另一种权衡下做的选择，不是 REST 的进化。

7. 总结：三条主线

可寻址性  ──→  资源有稳定地址 (URL)
   │
   ▼
安全 + 幂等  ──→  GET 可以重发
   │
   ▼
可缓存性  ──→  中间层可以加速
   │
   ▼
可扩展性  ──→  系统能跑到全球规模

REST 不神秘。它就是把 Web 之所以能成为 Web 的那些隐含假设，写成了显式约束。

理解这一条线，你就理解了：

  • 为什么 URL 设计是架构决策
  • 为什么缓存能成立
  • 为什么静态站没"过时"
  • 为什么 GraphQL 是另一种选择，而不是升级
