学习对象：只写过简单、面向过程 C++

这个网页联机飞行棋，到底是怎么跑起来的？

不从“框架”“架构”这些词开始。先把它当成：一台一直开着的裁判电脑，加上几位玩家各自打开的棋盘窗口。

Node.jsJavaScriptWebSocketHTML / CSS和 C++ 思路对照

0. 一句话先记住

服务器保存真实棋局，并负责判定规则；浏览器只负责让玩家点按钮、显示棋盘和动画。

你可以把它想成两份程序在配合：

服务器程序
裁判 + 房间管理员
⇄
你的浏览器
棋盘 + 按钮 + 显示器
⇄
朋友的浏览器
同一盘棋的另一扇窗口

不像普通单机 C++ 程序只在一台电脑上运行，这里玩家的浏览器和服务器通过网络一直保持通信。

1. 把项目文件翻译成你熟悉的 C++ 概念

项目文件大白话职责可类比的 C++ 内容
server.js一直运行，接收玩家动作，更新游戏，广播结果。main.cpp + 网络收发 + 游戏主循环
shared-rules.js飞行棋规则：怎么走、能否起飞、是否吃子、是否获胜。你拆出的 rules.cpp / 一组函数
game.js浏览器里处理按钮点击、接收结果、画棋子、播放动画。cin/cout 的“图形化升级版”
index.html网页上有什么：棋盘、按钮、文字、输入框。控制台程序的菜单和输出区域布局
styles.css颜色、大小、位置、动画、排版。不是规则；更像 UI 美工配置
protocol.md规定浏览器和服务器“说话”的格式。网络消息协议说明书

2. 先把“单机控制台飞行棋”想清楚

你曾写过的简单 C++ 程序，可能接近下面这样：

#include <iostream>
using namespace std;

int main() {
    int dice;
    int yellowPos = -1; // -1 表示还在停机坪

    while (true) {
        cout << "输入骰子点数：";
        cin >> dice;

        if (yellowPos == -1 && dice == 6) {
            yellowPos = 0; // 起飞
        } else if (yellowPos >= 0) {
            yellowPos += dice; // 简化版前进
        }

        cout << "黄色飞机位置：" << yellowPos << endl;
    }
}

这个网页游戏做的核心逻辑并没有本质变化，仍然是：

拿到操作 → 检查是否合法 → 修改棋局数据 → 告诉玩家结果

变化只有三个：

  1. 输入不再是 cin，而是玩家点网页按钮。
  2. 输出不再是 cout，而是更新网页上的棋盘。
  3. 游戏状态不放在你的控制台程序里，而是放在服务器内存里，让多个玩家都能看到。

4. 玩家点一次“掷骰子”时，究竟发生了什么？

① 你点“掷骰子”
→
② 浏览器发送
{type:"roll_dice"}
→
③ 服务器随机出 1~6
→
④ 服务器算哪些飞机能走
→
⑤ 服务器发新棋局给所有人

对应到面向过程的思路，可以想成服务器在调用：

void handleRollDice(GameState* game, const char* playerId) {
    if (!isCurrentPlayer(game, playerId)) {
        return; // 还没轮到他
    }

    int dice = randomInt(1, 6);
    game->dice = dice;

    findMovablePieces(game, playerId, dice);
    sendLatestGameStateToEveryone(game);
}

实际 JavaScript 的写法不同，但问题和步骤就是这个问题和步骤。

5. 玩家点一架飞机时，服务器如何当裁判？

浏览器不会说“我要走到第 18 格”，只会说：

{ "type": "move_piece", "pieceId": "yellow-0" }

服务器接到以后，依次检查：

  1. 这个人是不是已经加入了房间？
  2. 现在是不是轮到他？
  3. 他是不是先掷过骰子？
  4. 这架飞机是不是允许移动？
  5. 走完是否触发：起飞、同色跳 4 格、飞行格飞 12 格、终点反弹？
  6. 落点有没有对手的飞机？有则把对手送回停机坪。
  7. 四架飞机是否都到终点？有则结束游戏。
这就是“服务端权威”。玩家不能自己决定结果，服务器才是唯一的裁判。

6. 为什么不让浏览器自己算？

假设规则都写在浏览器里，玩家可以打开开发者工具，篡改逻辑。例如把“骰子随机数”改成永远 6，或者把飞机位置直接改到终点。

本项目让浏览器只发送“意图”，服务器才会：

玩家：我想掷骰子
服务器：你实际掷到 4

玩家：我想移动黄色 1 号飞机
服务器：你能走；走完是第 16 格；没有吃子；轮到蓝方
关键原则：客户端可以不可信；服务器的游戏状态才是真的。

7. WebSocket 是什么？不用死记术语

普通网页访问像“问一次、答一次、挂电话”。例如你访问一个新闻网页，浏览器请求内容，服务器把内容发回来，这次通信基本结束。

WebSocket 像一条不断开的电话线。 游戏过程中，服务器可以随时把新状态推给所有玩家。

玩家 A 掷骰子
  ↓
服务器立刻得出结果
  ↓
服务器同时通知 A、B、C、D
  ↓
所有浏览器更新为同一个棋局

因此不需要刷新页面，也不需要每秒轮询“对方动了吗”。

8. “房间”是怎么保存的？

服务器内存中有一个类似“房间表”的东西。可以把它想成你在 C++ 里用数组或容器保存数据：

rooms["ROOM1"] = {
    status: "playing",
    players: [黄方玩家, 蓝方玩家],
    gameState: {
        currentPlayer: "yellow",
        dice: 6,
        pieces: [...]
    }
};

这里实际使用的是 JavaScript 的 Map，它可以粗略类比为“按字符串查找数据的容器”。

当前项目的房间在内存里：服务器重启，房间和棋局会消失。因为没有接数据库。

9. 一个最重要的数据：GameState（棋局状态）

GameState 就是“当前整盘棋的所有事实”。它大概包含：

玩家
谁在房间、谁在线、谁是什么颜色、谁是房主。
回合
当前轮到谁，当前是“掷骰子”阶段还是“移动”阶段。
骰子
这回合掷到了几点。
飞机
每架飞机的颜色、编号、目前进度。
可移动飞机
掷骰子后，服务器列出哪些棋子可以点。
事件记录
起飞、跳格、飞行、吃子、获胜等日志。

前端收到它后，基本只做一句话的事情：“照着这份状态把页面画出来。”

10. 你现在最值得学习的代码阅读顺序

  1. 先看 README.md：知道运行方式和游戏规则。
  2. 再看 shared-rules.js：这是最接近传统 C++ 逻辑题的部分。
  3. 接着看 server.js：理解“收到一个请求后如何调用规则函数”。
  4. 最后看 game.js：理解网页如何发消息、收消息、更新画面。
  5. index.html 与 styles.css 放最后：它们更偏网页布局和美化，不是游戏规则核心。
阅读 shared-rules.js 时，先找哪些函数？

建议先找：创建初始棋局、掷骰子、移动棋子、判断可走棋子、结束回合、吃子、获胜判定。不要一开始就逐行读坐标数组；先理解“输入是什么、输出是什么、状态改了什么”。

阅读 server.js 时，先找哪些函数？

优先看：加入房间、开始游戏、掷骰子、移动棋子、接收消息。你会看到一个非常清晰的模式：收到消息 → 按消息类型调用函数 → 广播新状态。

12. 你可以先忽略的复杂部分

第一次学习时，不必立刻弄懂这些：

  • CSS 的所有属性和动画；
  • 浏览器 DOM 的每一个 API；

  • 自动重连、限流、消息大小限制；
  • 棋盘每个像素坐标为什么是这个数字。

先只看最主干的一条线：

点击掷骰子
→ 浏览器发消息
→ 服务器执行规则
→ 服务器返回新状态
→ 浏览器更新画面

13. 下一步练习：把它改成你自己的“小功能”

推荐按难度从低到高练：

  1. 修改页面标题或按钮文字。
  2. 在日志里增加一条“谁进入了房间”。
  3. 把每位玩家的完成飞机数量显示得更明显。
  4. 给骰子增加一个“最近 5 次点数”的显示。
  5. 增加“房主重新开始本局”的功能。
  6. 把房间状态保存到文件或数据库，让服务器重启后还能恢复。
前 3 个练习主要是浏览器显示；后 3 个开始会碰到“客户端发请求—服务端验证—广播状态”的完整流程。
